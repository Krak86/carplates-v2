### CSP report sink (finding #2; deployed 2026-11-08, policy gaps fixed from real reports, Telegram eval decision + ~1 week of traffic pending)

Reports are dominated by browser-extension / antivirus / ISP-injection noise, so the sink needs dedup + filtering; reuse Sentry rather than
building storage or adding a vendor.

- **Caddy:** add `report-uri /api/csp-report` to the policy (same-origin, so no new allow-list entry and no public Sentry key in the header).
- **API:** new `POST /api/csp-report` accepting `application/csp-report` and `application/reports+json`; `@Throttle`'d (open unauthenticated
  POST), Zod-validated, drops noise (`blocked-uri` of `chrome-extension:` / `moz-extension:` / `safari-extension:` / `about` / `data` / empty),
  forwards survivors to Sentry via the SDK. Follows the public-endpoint + `@Throttle` conventions (`common/throttle.ts`, CLAUDE.md).
- **Fallback (zero code):** point `report-uri` at the Sentry security endpoint and rely on its inbound filters (the public ingest key is then in
  the header; confirm the Sentry plan still accepts CSP reports).
- **Rollout:** deploy the sink → walk every flow for ~1 week (plate/VIN lookup, Google/Telegram/email auth, Turnstile, YouTube/Sketchfab/Maps
  embeds, Disqus, PostHog, share) → when the reports are clean, rename `Content-Security-Policy-Report-Only` → `Content-Security-Policy`
  in `infra/Caddyfile` and re-walk the flows on live. Check that it applies to the **SPA HTML and static assets**, not only `/api`.
- **Keep it running after enforcing:** its long-term job is catching third-party drift (a vendor adding a domain surfaces as a report, not a user-facing break).

## 5. Rules for every new feature (add to PR/commit review)

1. New `/api` endpoint: Zod input, a `@Throttle` if it enumerates, `SessionGuard`/`AdminGuard` if it touches user data.
2. User data queries always `where userId = session.user.id`; never trust a client-supplied owner id.
3. No `fetch` of a URL taken from a request; fixed host + `encodeURIComponent`d parts, a timeout, and a response size cap.
4. No raw-HTML sinks; no `sql.raw` with request-derived text; no `child_process` with a shell.
5. New embed/third-party origin → add it to the CSP allow-list and note why.
6. New cookie → `HttpOnly; Secure; SameSite`. New redirect target → relative paths only.
7. Don't log secrets, tokens, full plates tied to a user, or request bodies of auth routes.
8. User-uploaded files (planned photo shares): sign-in required, per-user active cap (3) + global storage cap, faces blurred server-side before storing, MIME + magic-byte check, size cap, no EXIF/APP segments stored, server-side recognition (never trust a client result),
   capability token stored only as a SHA-256, exact expiry/revoke enforced by the API (storage lifecycle is just cleanup), `noindex` + `no-referrer`, private bucket with its own scoped token.
